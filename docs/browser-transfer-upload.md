# Session-bound browser chunk upload and completion

`SenderTransferClient` now exposes `uploadPart(created, partNumber, chunk, signal?)` and `complete(created, signal?)` through the existing browser entry. The host uses the original object returned by that same client's `create` call. Copies, imported objects, altered responses, other client instances, and capabilities from an earlier account generation are rejected before transmission.

The client snapshots validated creation metadata and the upload capability in an in-memory weak binding. Every operation checks the current host account, generation, disposal state and upload deadline. It uses the transfer-scoped upload token, not the account Bearer token, for part/completion requests. Account changes cancel pending work; returning to the old account cannot revive the prior generation. The server remains responsible for actual token signature verification.

For each part, the host supplies an immutable Blob slice. The client validates its ordinal and exact expected byte length, including the final short part, and reads only that chunk. Web Crypto computes SHA-256 over those bytes, then a PUT to the fixed transfer/part endpoint sends the opaque binary buffer and `x-content-sha256`. One operation per client is admitted at a time. No full-file buffer, content analysis, persistent file copy, or automatic retry is introduced. Maximum chunk size remains the shared 64 MiB limit; choosing smaller chunks for slow links is a host responsibility.

Only a bounded, valid acknowledgement with `checksumVerified: true`, matching part count and consistent percentage becomes successful progress. The API supports explicit repeated part requests, but this client does not manage checkpoint resume or resolve uncertain upload outcomes automatically.

Completion POSTs to the fixed transfer endpoint using the same capability. A successful response must report complete/verified status, the expected total byte count and the host-supplied original whole-file hash. Its download window must match the shared four-hour rule, and its recipient path/token claims must be structurally bound to this transfer, download scope and expiration. Arbitrary external download URLs or mismatched hashes cannot be returned as verified completion. Token signatures are verified by the recipient server, not by the browser. After confirmed completion, this client refuses new uploads under that binding.

Reading, hashing, transport and JSON parsing share one per-operation deadline using the client's configured timeout (default 40 seconds, supported 1–120,000 ms). Requests reject redirects, cookies and cached responses; JSON is limited to 32 KiB. Cancellation releases response readers/bodies and prevents late replies from becoming progress or successful completion. A server write already started can still finish after the client aborts; callers must reconcile the existing transfer before deciding to retry. Completion rejection does not authorize delivery.

The host still supplies the sender-original whole-file SHA-256, file selection/slicing, progress UI, explicit retry/resume, recipient address, email composer integration and any mobile background-upload policy. These APIs do not hash a 500 GB file in one allocation or provide durable browser restart recovery. Server connection readiness and live integration adapters remain required; synthetic tests do not activate worldwide live sending. Transport-byte encryption through the key vault remains separate work.

Regression coverage includes scoped capability use, opaque binary preservation/checksum headers, part validation, copied/altered/foreign/expired capabilities, account changes during file reading, verified completion evidence, malformed progress, no automatic retry, overlap/disposal, bounded stalled stages and discarded late replies. A local HTTP fixture with real transfer/storage/token/checksum services verifies create → chunk upload → exact completion and unchanged stored binary bytes. No production file transfer or email was sent.
