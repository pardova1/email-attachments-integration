# Signed Stripe completion webhook

The server mounts `POST /v1/billing/stripe-webhook` before the ordinary JSON parser so verification receives the original body bytes. Configure `PAYMENT_PROVIDER=stripe`, the existing Stripe server API key, and the separate `STRIPE_WEBHOOK_SECRET` from the exact Stripe webhook endpoint. Production requires the live API key. The expected event mode is snapshotted from that key. Without a signing secret the route returns 503 and performs no application. Invalid partial configuration prevents startup.

Provision a snapshot-event endpoint for the application's own Stripe account and select `checkout.session.completed` and `checkout.session.async_payment_succeeded`. Prefer the adapter's pinned API contract `2025-02-24.acacia` for endpoint compatibility and verify against the real merchant account before use. This code does not provision the endpoint, retrieve secrets, create a merchant account, or send a live payment.

The verifier uses SHA-256 HMAC over timestamp + dot + raw body, checks v1 signatures using constant-time comparisons, and rejects timestamps over five minutes in either direction. Additional v1 signatures support endpoint-secret rotation; other signature schemes do not authenticate the event. Bodies are limited to 256 KiB, require uncompressed application/json, and are decoded as valid UTF-8 only after verification. Missing/bad signatures, modified bodies, stale/future headers, malformed events and wrong live/test mode fail without calling the payment provider.

Only the bridge's marked Checkout events are applied. Unsupported event types, Connect-account events, and unrelated products receive an ignored acknowledgement. A matching event must contain a properly scoped session reference and customer hint. The handler then re-fetches current payment evidence through the existing Stripe adapter; event-supplied paid flags and amounts do not authorize a grant. Verified customer identity must match the signed hint before the shared durable payment ledger is called.

A successful application receives HTTP 200. Duplicate deliveries and customer confirmation reuse the same payment reference and cannot add another license term. Concurrent delivery for one session receives 503 for retry while an admitted operation finishes. The global webhook processing budget uses the configured connection total, independently of other APIs; it also admits only one active operation per session per router instance. This is not a measured throughput or a cross-server limit.

This initial handler processes synchronously with a five-second deadline (composition accepts 1–30,000 ms). Provider/ledger failures, busy admission, and timeout receive generic 503 responses. It never acknowledges successful handling before application finishes. Late verification cannot begin a license application after timeout/disconnect. A transaction already started cannot be cancelled by the response deadline; the durable payment ledger makes subsequent retry safe. Provider calls retain their own bounded deadline. Slots/listeners are released after each attempt.

This is not a durable webhook inbox or background reconciliation worker. Stripe retry/manual replay must cover unsuccessful deliveries, and processing can time out during dependency outages. Event IDs are validated but not stored; grant idempotency is keyed by the shared durable payment reference, and duplicate delivery still re-fetches provider evidence. Provisioning, HTTPS hosting, real signature/version testing, outage/backlog recovery, and monitoring remain unfinished. Refund/dispute events are currently ignored, so a later refund does not automatically revoke an existing license; that lifecycle work remains required before relying on live commercial operation.

Regression tests use signed synthetic raw HTTP bodies and injected payment evidence. They cover exact-byte verification, key rotation signatures, stale/future/downgraded headers, mode/input/body limits, unrelated events, customer/evidence mismatches, shared confirmation replay, timeout before application, busy delivery and safe retry. No real Stripe event or charge was created.

Official references: [signature verification and delivery handling](https://docs.stripe.com/webhooks), [endpoint management](https://docs.stripe.com/events/manage-webhook-endpoints), and [Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment).
